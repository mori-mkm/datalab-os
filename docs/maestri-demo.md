# DataLab OS in Maestri

How to lay out a DataLab OS demo run as a Maestri workspace: one terminal per moving part, wired to the
same backend everyone already runs from `CLAUDE.md`. Maestri only hosts terminals and a browser tab here —
DataLab's own FastAPI/SSE stack (`src/datalab/api/`) stays the single source of truth for run state; nothing
in this workspace is a second authoritative log (see `.claude/handoffs/maestri-bridge-contract.md`).

## Prerequisites

- Repo root as the working directory for every terminal below (`.\.venv` and `apps\control-plane` must resolve
  relative to it).
- Python venv already set up (`.\.venv\Scripts\python.exe` runnable).
- `apps\control-plane` dependencies already installed (`npm install` has been run there).

## Terminal layout

Open one Maestri terminal per row. Each command is run from the repo root.

| Terminal | Command | Purpose |
|---|---|---|
| Backend | `.\scripts\maestri\backend.ps1` | FastAPI + SSE backend (`uvicorn`, `--reload`) |
| Frontend | `.\scripts\maestri\frontend.ps1` | Control Plane dev server (`npm run dev`) |
| Orchestrator | `.\scripts\maestri\orchestrator.ps1` | Run lifecycle + handoffs (top-level, no department) |
| Data Engineering | `.\scripts\maestri\engineering.ps1` | `engineering_lead`, `data_profiler`, `data_quality_analyst` |
| Analytics | `.\scripts\maestri\analytics.ps1` | `analytics_lead`, `eda_analyst`, `hypothesis_analyst` |
| Data Science | `.\scripts\maestri\modeling.ps1` | Modeling department watcher (`ds_lead`, `baseline_modeler`, `model_evaluator`) |
| Review | `.\scripts\maestri\review.ps1` | Review verdict events |
| Report | `.\scripts\maestri\report.ps1` | Report node events + artifact notifications |
| Browser Portal | open `http://localhost:3000` | Control Plane UI, once Frontend is up |
| File Tree | any terminal/file browser rooted at the repo | Watch `configs/`, generated run artifacts |

Each `scripts/maestri/*.ps1` file is a one-line wrapper around the CLIs shipped in
`src/datalab/maestri/run.py` and `src/datalab/maestri/watch.py` — see those files for the full flag set
(`--base-url`, `--run-id`, `--no-color`, etc.); the wrapper scripts intentionally take no arguments and use
the defaults (`http://127.0.0.1:8000`, newest run).

## Visual connections

Arrange the terminals so the wiring reads top to bottom, orchestrator fanning out to each department in the
order the graph hands work off:

```
Backend        Frontend (-> Browser Portal)
   |
Orchestrator
   |-- Data Engineering
   |-- Analytics
   |-- Data Science (modeling)
   |-- Review
   `-- Report
```

Backend and Frontend have no arrows into the department row — they are infrastructure the rest depends on,
not part of the handoff chain. Orchestrator connects to each department terminal because that is what its
filter actually shows: `run_started/run_completed/run_rejected/run_failed` and every `handoff_started` /
`handoff_completed` (department entry/exit), never the department-internal agent events (see the filter
rules in `.claude/handoffs/maestri-bridge-contract.md`).

## Running the demo

With Backend and Frontend terminals up, start a real run against the small synthetic config from any
terminal (or a dedicated one):

```powershell
.\.venv\Scripts\python.exe -m datalab.maestri.run --config problem.small --follow
```

`--follow` tails the run's own event stream in that terminal until a terminal event
(`run_completed|run_rejected|run_failed`); each department watcher started above attaches to the same
newest run independently and renders only the events its filter keeps. Add `--no-llm` to warn (not block) if
the backend isn't running with `DATALAB_LLM=off`.

## Saving the layout

Once the terminals are arranged and wired as above, save the workspace from the Maestri app itself as a
Partitura named **"DataLab OS — Runtime Orchestra"**.

Authoring a `.maestripartitura` file is out of scope for this repo: a Partitura is exported by the user from
the Maestri app's own "save layout" action, not generated by any script or code here.
